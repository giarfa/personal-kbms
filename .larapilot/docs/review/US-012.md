## Robert (code review)

- `- [Low]` `app/Meetings/EventColourRules.php` — deliberately not container-bound. Construction is a handful of array reads, and a singleton would go stale the moment a `config()` override changed the rule list. The cost is one rebuild per query call, which is why both call sites build it **outside** the row loop rather than per row.
- `- [Low]` `AgendaQuery.php:47` and `CalendarFeedQuery.php:47` — rule matching reads only `summary` / `location` / `description` / `organizer`, all already hydrated by the queries above it. The "no per-occurrence queries" criterion is **proven**, not asserted: `AgendaColourTest::test_colouring_adds_no_queries_to_a_dense_week` and its calendar twin count queries with `DB::listen` across a 30-occurrence window and assert equality with rules on and off.
- `- [Low]` `AgendaRow.php:39` — the `?EventColourRule $colourRule = null` default is what keeps `MeetingController`'s detail-page row uncoloured. Putting the exclusion in the constructor rather than in a Blade omission means a later view edit cannot accidentally colour the detail page. Documented in the property docblock so the default is not "tidied away" later.
- `- [Medium]` **Channel independence is enforced by CSS property, not by convention.** The fill rules set `background` (and, on the calendar chip only, `color`) and touch no border property at all, so coverage keeps its edge borders and marks on a coloured event. `:not(.kb-ev--cancelled)` / `:not(.kb-row--cancelled)` is written out explicitly rather than relying on source order, so reordering the stylesheet cannot silently un-cancel an event. This is the finding most worth re-checking on any future CSS edit: adding a `border` line to a `--colour-` rule is what would make one channel eat another.
- `- [Low]` The agenda row fill deliberately does **not** recolour its text, unlike the calendar chip. The row's three columns already carry their own colours, and tinting the row would push the already-marginal `--muted-foreground` meta line further down. See the Lars note below.
- `- [Low]` `resources/js/calendar.js` needed **no** change: the class arrives through FullCalendar's own `classNames`, and `eventDidMount` already writes `accessibleName` onto the element. Verified rather than assumed.
- `- [Medium]` **Pre-existing flakiness surfaced and fixed:** `CalendarFeedQueryTest::test_coverage_combinations_are_reflected_in_class_names_and_extended_props` asserted exact `classNames` on events built from `CalendarEventFactory`, which sets `location` only 50% of the time. Once the shipped "location is empty" rule landed, that coin flip decided whether the test passed. Fixed by setting `location` explicitly on those four fixtures, and the default rules were left **active** rather than cleared — the test now also demonstrates that the colour channel stays out of coverage's way. Every new test in this spec follows the same discipline.
- `- [Low]` Git discipline: one atomic Conventional Commit per task (`TASK-00`…`TASK-07`), each carrying `US-012` and its task id, no commits on `main` or `develop`, no push (correct for `git_mode: GITFLOW`).
- `- [Low]` No Eloquent model, migration, factory or seeder touched — rules are configuration over existing columns, so the same-task factory/seeder rule does not apply. `migrate:fresh --seed` unaffected.

## Lars (security)

- `- [Medium]` **The injection surface this feature could have had, and does not.** `colour` never reaches markup as a value: it is validated through the `EventColour` enum and only ever used to build a class-name suffix from a closed set, with the actual colour resolved from `--kb-rule-*` tokens in the stylesheet. A configured `#ff0000` or `red; background: url(...)` is not a colour — the rule is dropped whole, and `CalendarColourTest` / `AgendaColourTest` assert the raw value never appears in the page source. `label` is operator-supplied free text, rendered through Blade's `{{ }}` (escaped) in both legends and both row/chip labels, and delivered to the calendar through JSON into `setAttribute('aria-label', …)`, which does not parse HTML.
- `- [Low]` `config/kbms.php` is a repo file, not user input, and this key is deliberately **not** env-backed — so there is no path by which an unprivileged value reaches the rule set.
- `- [Low]` `EventColourRule::fromArray()` fails closed on every malformed shape, including the non-obvious one: a `contains` rule with an empty needle, which `str_contains($x, '')` would otherwise make match every occurrence. Guarded twice — once at construction, once in `EventColourCondition::matches()`.
- `- [Low]` No new route, no new request parameter, no authorization surface, no persistence change, no dependency change. `composer audit` scope unchanged.
- `- [Low]` **Contrast, and one honest caveat.** Every `--kb-rule-*` token reuses the oklch lightness pair of the already AA-verified `--kb-note` / `--kb-transcript` tokens (`0.45` on `0.955` light, `0.80` on `0.28` dark), so the ratio carries over by construction — ≈4.8:1 and ≈5.9:1. What that does **not** cover is `.kb-row__meta`, which uses `--muted-foreground` and already fails AA against `--card` (≈3.6:1) before this spec; on a tinted row it drops to ≈3.25:1. Pre-existing, marginally worsened, and the reason the row fill does not also recolour text. See Parent actions.
