## Robert (code review)

**Verdict: APPROVE.** No Critical, High or Medium findings. Month arithmetic verified exhaustively rather than by inspection: years 1900–2200 × every month × `delta` ±1 × `dayOfMonth` 1–31 (~223k cases) all landed in the expected target month, were real dates, and were clamped only when the source day exceeded the target month's length. December→January rollover, leap years (2024, 2000, 2100 non-leap) and negative deltas all correct.

- [Low] `resources/js/calendar.js` — `formatIso()` duplicated the zero-padded ISO join that `addDaysToIso()` already inlined; the shared helper was added without refactoring the existing function onto it. **Fixed.**
- [Low] `resources/js/calendar.js` — `addMonthsToIso(iso, delta, dayOfMonth)` ignored the day component of its ISO argument entirely; the sole caller built a synthetic `…-01` string just to satisfy the signature, and a future caller passing a real date would silently lose its day with no error. **Fixed** — replaced with `monthStepToIso(year, month, delta, dayOfMonth)`, which takes a year/month pair and so cannot be handed a date it would discard.
- [Low] `resources/js/calendar.js` — stale-`pendingFocusDate` path. If FullCalendar's DOM commit ever lagged Alpine's `$nextTick`, `focusOn()` would find no cell and fall through to `calendar.gotoDate(isoDate)`; for the month branch that target is inside the already-rendered month, so the date profile would not change, `datesSet` would not re-fire, and `pendingFocusDate` would stay set — dropping focus and letting the next `datesSet` consume a stale target. **Not fixed:** structurally pre-existing (week and day rely on the same precondition and predate this rework); month is simply the view where the fallback is guaranteed to be a no-op. Recorded here rather than fixed under a rework scoped to one finding.
- [Informational] `resources/js/calendar.js` — the helper's docblock claimed "pure", but `daysInMonth()` reads the host's local timezone through `new Date(year, month, 0)`. Tested under `America/Santiago`, `America/Havana`, `Asia/Tehran`, `Australia/Lord_Howe`, `America/Sao_Paulo`, `Pacific/Apia`, `Europe/Rome`, `Asia/Amman`, `Asia/Beirut`, `Africa/Cairo` for 1970–2100 — zero discrepancies, so no correctness impact. **Docblock wording corrected**, since "pure and inspectable" is the stated justification for shipping without a JS test runner.
- [Informational] `resources/js/calendar.js` — `Math.floor(zeroBased / 12)` with `(zeroBased % 12) + 1` is correct only for `zeroBased >= 0` (JS `%` is remainder, not modulo). Unreachable: FullCalendar emits 4-digit ISO years, so `zeroBased >= 12`. Left as is.
- [Informational] `resources/js/calendar.js` — anchor derivation verified against the installed library, not just the plan: `@fullcalendar/core` 6.1.21 computes `buildPrev`/`buildNext` as `startOf(currentDate, currentRangeUnit) ± dateIncrement`, and `getDate()` returns that same `currentDate`. The rendered month after `next()`/`prev()` is therefore exactly `anchorMonth ± 1`, so the queued target is guaranteed to exist in the new grid. Week and day branches are byte-equivalent to the previous `stepDays` logic — no behaviour change, as required.
- [Informational] `resources/js/calendar.js` — month is the `else` fallback rather than an explicit `=== 'month'` branch. Cosmetic given the fixed three-view `viewMap`. Left as is.
- [Informational] `.larapilot/docs/test-results/US-008-manual.md` — paging *backward* while focus sits on a leading cell of the previous month correctly leaves the focused date unchanged (September grid, focus 31 August, `PageUp` → August grid, ring still on 31 August). ## Lars (security)

**Verdict: GO.** All findings Informational — no security defect in the rework diff.

- [Informational] `resources/js/calendar.js` — **no unbounded navigate/re-queue cycle is reachable.** `pageView()` computes the target *before* moving the calendar, from `calendar.getDate()`; FullCalendar keeps `currentDate` inside `currentRange`, so in `dayGridMonth` the anchor is always a date in the displayed month. The target is `anchorMonth ± 1` with the day clamped by `daysInMonth`, i.e. always a real day of the month about to be rendered, and `dayGridMonth` renders every day of its own month. `cellFor()` hits on the first `datesSet`, so `focusOn()` takes its `if (cell)` branch and never reaches the `gotoDate` re-queue. The one theoretical loop shape — a target FullCalendar cannot resolve, so each `gotoDate` yields a fresh non-equal `dateProfile` and re-fires `datesSet` — requires a `NaN`/`Invalid Date` target, ruled out below.
- [Informational] `resources/js/calendar.js` — input trust sound. `focusedDate` is seeded from `config.initialDate`, rendered as `$range->anchor->toDateString()`; `CalendarRange::fromRequest()` rejects non-string `?date[]=` shapes and catches parse failures, so it can only ever emit a well-formed `YYYY-MM-DD`. Thereafter `focusedDate` is reassigned only from `cell.dataset.date` or from these helpers. No path reaches the parsing helpers with a malformed string, so the `NaN` propagation they would otherwise permit is unreachable.
- [Informational] `resources/js/calendar.js` — no DOM XSS surface. The new helpers are pure string/number math: no `innerHTML`/`outerHTML`/`insertAdjacentHTML`, no `eval`/`Function`, no attribute or URL construction. Their output is consumed only by a `dataset.date === isoDate` equality comparison and by `gotoDate` — never interpolated into a selector.
- [Informational] `resources/js/calendar.js` — no change to the `/calendar/events` contract. The `events` fetcher is untouched; request shape stays `?from=&to=` sliced from FullCalendar's own range, and frequency stays one fetch per page turn — the new focus target resolves in-range, so it adds no `gotoDate` and no extra round trip. `CalendarEventsController::window()`'s `MAX_RANGE_DAYS` clamp remains the real bound and is unaffected.
- [Informational] `package.json` / `package-lock.json` / `composer.json` / `composer.lock` unmodified in `722aead..HEAD`; no dependency added or bumped, so round 0's clean `composer audit` / `npm audit` still hold and need no re-run.
