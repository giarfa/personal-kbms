## Lars (security)

- [Medium] `app/Calendar/IcsParser.php:33` — `VCalendar::expand()` eagerly materializes every occurrence inside the window before the generator yields. A hostile/compromised feed with a high-frequency `RRULE` (`FREQ=SECONDLY`/`MINUTELY`/`HOURLY`) forces sabre/vobject to build a very large number of `VEVENT` objects synchronously on one fetch. Only `FREQ=WEEKLY` is covered by the unbounded-series test; no frequency/occurrence-count cap exists anywhere in `IcsParser`/`IcsFeedClient`. Accepted as a follow-up hardening item — `KBMS_ICS_URL` is operator-configured, not attacker-supplied per request.
- [Medium] `app/Calendar/IcsFeedClient.php:38-39` — no response-size guard (no `Content-Length` check, no streaming, no max-bytes limit) before the body reaches `IcsParser::parse()`. Same accepted-follow-up rationale as above.
- [Low] `app/Calendar/IcsFeedClient.php:44` — default Guzzle redirect-following isn't restricted; SSRF-adjacent if the configured feed host were ever compromised or DNS-rebound. Low severity — URL is operator-configured on a single-operator local tool.
- [Low] TASK-01 commit message claims `composer audit` was run clean; no CI artifact independently verifies it (confirmed manually during this session — `composer audit` reports no advisories).
- [Info] No issues on mass-assignment (`$guarded = []` arrays use fixed hardcoded keys, feed content controls values only, never column names), logging/PII (`SyncCalendarFeed` logs only run id/status/error/counts), access control (no new routes, still console/job/doctor-check only), or `security.txt`/`SECURITY.md` scope (correctly untouched).

**Verdict: GO with notes**
